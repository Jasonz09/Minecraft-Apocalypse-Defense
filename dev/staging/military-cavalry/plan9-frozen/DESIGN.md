# Cavalry: compound ownership before a mounted soldier

## Scope and feasibility

The original roadmap calls for cavalry outside patrols, rapid support and counteroffensives (docs/ROADMAP.md, Physical civilization population). It does not approve a fixed soldier mix. Horse/rider compatibility is explicitly a native gate. This stage does not introduce an actor, horse asset, selection or second owner into production.

Installed @minecraft/server2.7 declares EntityRideableComponent.addRider/getRiders/ejectRider and EntityRidingComponent.entityRidingOn. addRider returns success and may throw; success alone does not prove both directions agree. The official mount_pathing goal describes mounted target seeking, so an AI path is plausible; it does not prove a custom human on a custom horse will navigate, attack, respect home or fit city gates correctly.

Current population admission increments one per group in population/lod.js. Current creation-binding-v2 stores exactly one actor ID/type per group. A horse spawned through another component, timer or helper would be invisible to that identity record and could survive rider death/unload/teardown. **Do not add a horse to that single-actor protocol.** A one-entity horse-and-human geometry also would not prove rider/mount gameplay.

## Smallest cohesive production slice, after the current creation foundation

1. Add a versioned compound record to the same creation store (future core schema3, not the kingdom schema3). Preserve old single-actor records and exact issuance inventory; do not reinterpret them or silently erase receipts. One pair record binds immutable group/epoch/human birth generation plus rider and mount role IDs, type IDs, native-instance generations, canonical/pair tokens and independent pending/alive/terminal phases. Every role gets durable intent BEFORE spawn. A pending role never means never-created after restart.
2. Selection adds a later cavalry class/schema alongside the reviewed schema1 swordsman/schema2 archer. The existing per-group type resolver selects the rider, while a class-aware physical cost is2. Update the same LOD/reducer admission and owner budgets: global24/district8 are actual actor ceilings, including mount, rider and pending reservations. No new cap or fixed mix. One spawn-per-hour budget can create pair parts across hours; reserve both physical slots first. Ordinary other groups remain eligible; unresolved pair creation holds only that pair, retaining its reservation safely.
3. Only popSync may spawn/remove either role. Rider gets the existing one canonical civpop group tag plus a pair-role generation token. Mount gets a derived pair-role token, NOT a second canonical population group or five more soldiers. Bind exact spawned IDs before any seating. Do not adopt an untagged horse or use a nearby animal from a namespace-only query. Rejoin resolves only exact issued IDs and role tags; absence holds.
4. Add a custom mount with one rideable seat, family restricted to cavalry riders, pull_in_entities=false and no player-control/taming/breeding/automatic spawn behavior. There must be no automatic find_mount behavior that can take another pair's horse. New rider/mount assets are a later reviewed data patch, retaining owned humanoid art and primary built-in references where verified. No global vanilla-horse override.
5. Seat only a freshly unique exact nearby pair (suggested max2blocks), after fresh loaded **two-entity** footing/swept width/combined mounted-height clearance. Current foot-villager0.6width/2high corridor is insufficient. Capture metadata/policy, fresh native role identity and both relationship directions before addRider; verify getRiders exactly riderID and rider.riding.entityRidingOn exactly mountID afterward. The normal owner does this within its existing bounded callback. No teleport, blind distant addRider or extra scheduler. False/throw/disagreement holds; a retry may reuse those SAME IDs only, never spawn more parts.
6. Use the existing one death subscription for both types. A fresh verified rider death and horse death are distinct: horse loss must never subtract represented human soldiers. Soldier casualty accounting remains the separate covered-cohort authority; no new aggregate debit here. entityRemove, loaded absence, empty getRiders or unseated state never means death. First slice may safely demote a surviving rider to tracked on-foot/cleanup state rather than automatically remount; no replacement horse until an explicit positive lifecycle policy exists.
7. Gate-off/LOD/removal must clean both issued roles through the same positive removal protocol. Persist per-role removing intent, recheck exact native identity/loading/relationship, remove the exact actor, positively observe success, then publish its terminal receipt. Partial success remains tracked across restart. Pair retires only when BOTH roles have positive terminal receipts. Rider death leaves a tracked mount requiring owner cleanup; horse death leaves a tracked rider. A terminal actor that reappears refuses—never delete/rebind it automatically.
8. Extend strict census, creation allowed types, death filters, starter/export preservation, status and physical caps in one cohesive central change. Existing owner duplicate vulnerability must not be inherited by an untracked companion. Full fault/compatibility gates precede disposable native tests; no cavalry selection should be enabled early by merely adding its type string.

## Inspectable minimum in this folder

lifecycle.mjs is a small PURE bounded decision model. It validates immutable pair identity, canonical-vs-mount role tokens, primitive loaded snapshots and physical cost2. It holds missing/ambiguous/pending parts; returns tracked survivor cleanup requests after positive terminal facts; refuses distant seating; requires fresh two-body proof before a seating request. Every result has writePermission=false and aggregateDelta=0. Returned requests are NOT native capabilities, spawn tickets, durable receipts or proof the supplied death facts are authentic. No world/store/entity import exists.

Nine focused cases pass,69.153ms; strict root-option isolated TypeScript passes. These cover unload/rejoin-style missing snapshots, duplicate/wrong/stale role identities, exact gate-off requests, separate rider/mount positive deaths, partial terminals, issuance crashes, cost2 ceilings, nearby seating and invalid numbers/dimensions. This is a lifecycle specification with executable negative controls—not a durable store/controller or cavalry implementation. No native actor was spawned or seated.

## Next native micro-gate after safe compound owner integration

Use a separately verified fresh fixture and one selected existing soldier group. Let the sole owner create exactly two tracked actors across its normal budget. Verify both exact IDs/tags and physical accounting, then verify both mounting directions and human/horse appearance in a broad safe open lane. Save/rejoin and confirm same two IDs, no new actors. Test gate-off and rejoin after each role's removal. Only then test one controlled rider death and one controlled mount death, demonstrating survivor tracking/no absence replacements/no human debit for the horse. Mounted combat, home/pursuit, stairs/water/gates, patrol/support routing and reinforcement/casualty coverage remain later gates.
