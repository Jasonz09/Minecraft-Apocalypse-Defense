# Sequential verified source summaries — design only

Production is frozen during root full55899. No implementation, production/test edits, new benchmark, runtime memory result or native stability proof is included here. The original native hold-time mismatch is still unknown. WAIT recovery of the existing receipt remains the immediate priority; a new policy or receipt version is unnecessary for this future memory work.

## Observed retention path

`districtplan.js` stores regenerated-op closures in private `LAZY_OPS:WeakMap<record,Map<element,producer>>`. Each producer retains its element production dependencies and drop set; some dependencies retain planning/ground structures. `loadSavedRunSteps` also returns a broad wrapper containing master, record, queue, region and payload. The leaf command retains five records, while every record remains a WeakMap key, so its producer values remain reachable. The record itself contains ground summary metadata, not the original full ground payload. Root's offline profile reports five-record post-GC heap97.811MiB and final delta88.653MiB, versus discard-mode post-GC examples12.392–32.762MiB. These measurements are Node/fake-world behavior, not Bedrock memory attribution, reclamation timing, warning thresholds or a working replacement pipeline.

Releasing only after wall enumeration is UNSAFE: the current preview and core compiler still scan every stage of every source for historical decor, later AIR/gate/dressing claims, exact own final operation and neighboring final material claims. Pending receipt recovery likewise must recompile the original admitted coordinates. Deleting `LAZY_OPS` after final immutable LeafPlan compilation could reduce retention during commit/wait, but does not address multi-source loading peaks or D3 loading warnings. No release-only patch is proposed as a peak-memory remedy.

## Target architecture

Retain at most one complete rehydrated source wrapper/record at a time. Maintain one exact raw-source/protection guard captured before any loading, a small expected source manifest, a bounded selected-wall survey, and a bounded in-memory summary. Never persist these summaries or treat arbitrary deserialized summaries as provenance.

1. Validate all existing kingdom sources, exact/unique district indices, completed dimension/checksum/master identity and orphan original job keys using the current rules. Capture the raw guard before cooperative work. Read/validate leaf receipt keys under existing bounds and parser. Unknown, multiple unfinished, malformed or source-incompatible histories refuse. A pending schema2/v1 receipt supplies only its original requested coordinates; it grants no source or block write permission. Keep its exact raw CAS stamp and all identity/digest semantics.

2. **Pending receipt path:** the original14 coordinates are already known from the validated receipt. Build their27-cell union (at most1728 unique cells). Rehydrate and verify each source sequentially, summarizing only these wanted cells while still iterating and coordinate-validating EVERY op of EVERY stage. Then let the verified wrapper, op arrays and producer closures leave a dedicated load-and-summarize helper before loading the next source. Keep only scalar district/checksum/master/complete-queue proof metadata and summary claims. A source is counted verified only AFTER its entire guarded load and all-stage summary finish successfully.

3. **No pending receipt path:** rehydrate the selected source first. Reproduce the current selected-wall enumeration in stage/element/op order, including later overwrite behavior and its existing wall-target cap. Survey EVERY enumerated selected wall target with current read budgets. Preserve exact total/surveyed/unloaded/tree/present/other counts and bounded unreadable samples. Collect up to64 ALL observed tree-occupied coordinates (including logs, vines, persistent/unknown leaves and protected/foreign-adjacent cases); track truncation and refuse admission if capped. Do not filter for apparent eligibility yet. Unloaded wall targets stay explicitly unreadable/incomplete and never gain write permission. Do not silently reinterpret an empty loaded candidate set as a complete-world clean bill.

4. Once all observed candidate coordinates are known, scan ALL selected-source stages again into the bounded contact summary, then release that source wrapper. Load each remaining verified neighbor sequentially and scan all its stages into the same wanted-cell summary. At most one heavy source is retained. This selected extra pass is necessary because survey candidates were not known before wall enumeration. No planned vegetation/decor or foreign final claim can be dropped because a candidate currently looks benign.

5. For each wanted coordinate retain BOTH (a) an ever-seen historical-decor veto bit, and (b) the exact last operation per district, including stage, original element index and cloned complete operation, with AIR and nonmasonry claims retained. The existing preview and strict compiler have slightly different expected-contact projections: preview collects each source's final masonry ID; strict compiler accepts a neighboring planned material only if all final claims agree on the same stateless masonry. Preserve both existing results from the same exact last-op summary; do not silently make preview's weaker display classification into write authorization.

6. Finish only after the verified summary source set equals the entire expected source set, with no duplicate/unknown/missing district and exact original checksums/master/dimension/completion. Derive current preview classifications with fresh27-contact reads, historical vetoes, protection and expected-material rules. Keep all refused and unreadable rows/counts in the returned survey. Only then form the eligible admitted coordinate list using the existing policy. For an unfinished receipt, use its original requested coordinates and immutable before snapshots instead; never replace that list with the latest remaining leaves.

7. Reconstruct the EXACT existing LeafPlan body from summary claims, in original requested-coordinate order, using the unchanged policy/version, source ID sort, target operation bytes, contact cube order, historical booleans, strict expected material arrays and refusal reasons. Do not add summary fields to the signed body. `compileScannedOps` stays the exact full-source op count but outside plan identity. Pending native plan must remain `c835b06e`; receipt schema2 and raw-before/digest values must remain valid under the unchanged parser. The finished plan contains only <=64 targets/1728 contacts plus metadata; release summary maps and all remaining source wrappers before commit/wait.

8. Use the SAME exact commit,56-read ceiling, cached final Block handle, full snapshot equality, current all-neighbor protection, source/CAS barriers, readonly preview and bounded WAIT behavior. Streaming grants no block-write exemption. It must fail before any block mutation if source loading or summary completion is interrupted or rejected.

## Guarding and lifetime rules

All generator boundaries, including loading, summarizing, wall enumeration, live survey and finalization, remain bracketed by the same raw-key/raw-string/protection/cancellation guard. Each source's queue checksum/spec and master comparison remain mandatory, not inferred from a previous district. Preserve exact original source-key and all-key byte/count quotas. New in-memory summary must have explicit coordinate/source/claim caps; any overflow refuses rather than dropping last writers or historical flags. No unloaded block triggers chunk loading.

Use a separate nested generator/helper whose return value contains only a compact summary contribution and scalar proof metadata. Do not return or cache payload, ground JSON, live record, op producer, generator, iterator result or references to source operations. Do not keep `saved` in a long-lived outer scope. WeakMap entries become reclaimable when those record keys leave scope; explicit deletion is optional later defense, not a reclamation guarantee. A unique internal capability or module-private WeakMap can brand a complete accumulator so generic parsed objects cannot bypass the verified streaming orchestration. Test seams remain explicit injected dependencies.

## Minimal future code split

Extract the existing compiler's wanted-cell accumulation and exact final-plan assembly into private pure helpers reused by batch and sequential paths; avoid maintaining two versions of historical/final ownership rules. Add a guarded streaming orchestration only to the leaf-maintenance command, using the unchanged saved-run loader. Keep ordinary construction/site generators and all other consumers untouched. A wall-census helper may be split from current preview so candidate collection precedes neighbor summary classification without changing either operation. No production patch is provided until those shared helpers and their exact-parity tests exist.
