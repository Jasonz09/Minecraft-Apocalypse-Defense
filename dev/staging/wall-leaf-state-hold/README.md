# Native partial leaf batch: source investigation only

Installed157 native confirm reported one write attempt and one verified replacement, then HELD: `admitted leaf identity/states changed; preserve target and receipt`. This is a safe partial result, not repair completion. Native before/current state difference is not yet known.

Three lightweight tests execute actual production core with synthetic injected cells: `node --test dev/staging/wall-leaf-state-hold/state-hold.test.mjs` passed3/3,203.3216ms. A synthetic update_bit false-to-true after the first replacement reproduces the exact hold and keeps the second target and incomplete receipt unchanged. A different leaf type or unrelated state insertion/removal produces the SAME error. The native message alone therefore cannot establish update_bit as the cause. Persistent leaves, copper contact and protected columns still refuse.

Current core captures ALL sorted target block states during separate admission. At commit, it redoes27-contact proof and compares the current target snapshot with the immutable receipt before doing a second27-contact proof. The second proof and final target read must also match; all source/CAS/protection barriers remain. The observed error is from the first admission comparison, so the target was still classified eligible (readable nonpersistent leaf). It could differ by type or any state field, not necessarily update_bit. No source modification is proposed before the exact native difference is obtained.

Existing leafpreview prints current type and persistent_bit but not every block state. The tree diagnostic likewise does not provide an exact all-state target dump. A bounded read-only diagnostic could later report first pending target coordinate, receipt `before` type/states and a fresh getAllStates() snapshot, each bounded by existing64-state constraints, with no setters/property writes. A native testforblock state test can test a known hypothesis; it cannot recover every unknown state. Official command reference: https://learn.microsoft.com/en-us/minecraft/creator/reference/content/commandsreference/examples/commands/testforblock?view=minecraft-bedrock-stable

Recovery design to review ONLY after evidence: keep existing pending-v1 receipt held and immutable. Do not reinterpret it through a looser v2 parser or automatically readmit its targets. A separate explicit v2 policy/key must reject pending v1 and unknown histories; resolving that retained pending batch requires a separately reviewed migration/recovery contract, not deletion. For NEW v2 batches, if native evidence and supported state semantics justify one engine-maintained boolean field, preserve exact type, explicit persistent_bit=false, exact state-key set and every other metadata value. Only that explicitly proved boolean field could differ between admission and a later commit. Still require exact full snapshot equality between the first27-contact proof, second27-contact proof and final read within the commit slice, including that field. This avoids ignoring within-commit races. No arbitrary metadata exclusion, persistent-leaf conversion, source/ore/foreign/protection exception, additional felling permission or historical source relaxation is acceptable. The immutable original snapshot stays in the receipt; fresh proof rather than receipt rewriting grants any future write.

Required future negative cases: absent/nonboolean/extra field; changed type/persistent/other field; changed field during second proof/final read; source/protection/foreign/copper changes; pending-v1/unknown journal; interrupted setter/checkpoint and idempotent present masonry. No v2 implementation, production/central test/UI/install changes or native recovery acceptance is included here.
