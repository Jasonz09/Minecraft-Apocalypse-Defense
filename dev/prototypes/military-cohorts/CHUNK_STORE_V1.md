# Isolated archive chunk store — metadata protocol v2

**Prototype only.** `chunk-store-v1.mjs` accepts an injected synchronous `{get(key),set(key,value)}` persistence model. It imports Node's SHA256 and is **not a Bedrock-runtime-ready module**. No native property, entity, pack, timer, production schema or installed file is changed. Existing v1/v2/archive-v3 experiments and their 60 checks are untouched.

The original metadata-v1 prototype passed its 80 tests but failed independent evidence-preservation review: a valid foreign standby could be overwritten, and foreign/future standby metadata injected after a journal-only crash could be deleted. All three failures are reproduced in `chunk-store-standby-before.json` against source SHA256 `b43b9dbc18ab54fe5f02d2f4572b254e5c6660c7be87a119693c4b03d159ed18`. They did not involve a native world. The current file name is retained, but manifests and journals now use strict protocol version2. Unknown/older-v1 receipts refuse implicit migration rather than being rewritten.

Mojang's primary release note explicitly sets a 32,767-byte string property limit and uses `undefined` to remove a property: [official 1.20.40.20 Script API notes](https://feedback.minecraft.net/hc/en-us/articles/19244682051341-Minecraft-Beta-Preview-1-20-40-20). The current [official World API reference](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/world?view=minecraft-bedrock-stable) describes dynamic-property get/set and errors; it does **not** promise multi-property atomicity, write-ahead disk flush order or replay of a death event. Those guarantees are not inferred here.

## Fixed storage and publication

The namespace has exactly 12 possible keys: authoritative `head`, `journal`, and two banks each containing one manifest plus four chunk slots. Data chunks are at most 24,000 UTF8 bytes; payload is at most 96,000 bytes. Metadata/journal strings also enforce the 32,767-byte property ceiling. UTF8 splitting preserves codepoints and measures actual bytes, including astral symbols; the validated archive roster itself uses ASCII identities. No 96KB value is passed to a native-shaped property setter.

`createArchiveChunkStore(kv,{prefix})` returns `load`, `publish`, `recover` and its fixed key inventory. A prefix is bounded and explicit. No property enumeration, broad clearing, world writes or automatic stale-data adoption exists.

1. Validate the supplied archive-v3 state. Load the exact existing head and pending journal; refuse pending/unknown/corrupt/future state before a new publication. Require the caller's exact `expectedHead` token. Subsequent states retain lineage and advance revision by exactly one; an identical validated state is a zero-write no-op.
2. Choose the inactive bank. A nonempty standby must be in that exact bank, share lineage, have precisely the current head's previous sequence/revision, and match the SHA256 of the prior authoritative head recorded in the current manifest. Plausible counters alone are not permission. Each manifest records only one bounded prior-head hash, not a recursively growing chain. Write a version2 journal binding the exact previous head, proposed next head and authorized prior standby token (or null).
3. Recheck that staging metadata is exactly the captured prior token or staged-next token, and that each existing chunk is an authorized old/new digest or already cleared. Unknown bytes/metadata refuse in place. Write all four inactive chunk slots (clear unused slots with `undefined`), each with exact readback. Write the bank manifest and verify every chunk byte count, SHA256, aggregate digest, canonical JSON and strict archive-v3 invariants. Verify the old authoritative bank again and freshly reverify staging and both ownership stamps.
4. Publish the single authoritative head property **only after complete staging verification**. Re-read/validate the now-authoritative bank, then clear the journal with readback. Each normal publication makes exactly 8 setter calls. Readers never select an unpublished bank.

SHA256 detects content mismatch; it is not a signature or proof that an external actor is authorized. A state/revision token is optimistic concurrency checking, **not native compare-and-swap**. The store requires one serialized writer and fresh reads. A local reentrancy guard and repeated head/journal stamps detect injected changes; they cannot provide a global lock against arbitrary concurrent adapters or an ABA writer.

The full-cap sizing fixture has 32 provinces, 256 pools, 128 working births, 128 archive ranges, 128 bindings and 32 covered snapshots. It serializes to **77,471 bytes**, four data chunks, maximum property 24,000 bytes, and 97 injected reads through initial publish plus a verified load. Both banks and the journal are fixed-capacity; history does not accumulate extra keys. The 96KB model ceiling remains separate from the native per-property ceiling. Actual maximum saved-data growth still obeys archive-v3 bounds; storage does not bypass them.

## Recovery decisions

- **Old head unchanged, valid journal:** roll back only the unpublished inactive bank, then clear that journal. The prior committed bank/head remains untouched. Rollback uses at most 6 delete calls; repeating after interruption is safe. The captured prior/next metadata token and allowed chunk digests are checked before every destructive delete. Unknown, foreign, same-lineage future, forged-past or corrupt staging refuses cleanup even when the head/journal stamps remain unchanged.
- **Proposed head already published, valid full payload:** finalize by clearing only the matching journal. Never roll back a verified published roster because the caller saw an exception after the head write.
- **Corrupt/future authoritative manifest, inconsistent payload, missing head with owned data, conflicting journal or foreign stamp:** refuse/quarantine in place, with no automatic fallback to a previous state. Reverting a newer casualty roster to an older valid bank could resurrect killed soldiers; availability is sacrificed rather than silently changing authority.
- **Clean empty namespace:** report absent. An interrupted initial journal reports pending, not a fresh world. Orphan banks/chunks without a journal refuse initialization.

`load()` returns `ok/absent/pending/refused`, the exact head token, decoded state when available, and `writable:false` while a journal is unresolved. A valid old state can be displayed during staging but must not drive new mutations until recovery. `publish` can return `interrupted-or-refused` after an exception **even if the new head committed**; always reload/recover, never infer rollback from `ok:false`. `recover` never restores a previous head over newer authority.

## Tests and limits

Run `node --test dev/prototypes/military-cohorts/*.test.mjs`.

**88/88 combined standalone checks pass** on 2026-11-05 (28 store cases plus the unchanged 60 accounting cases), zero failures/cancellations/skips, recorded duration 4,955.4079 ms. Output: `chunk-store-v2-standby-focused.log`. This is not an active-pack full verification result. The earlier `chunk-store-v1-focused.log` retains only its original 80-test snapshot proof.

Store checks include: before/after every one of 8 initial/update writes, with both blank and authenticated historical standby; every one of 6 rollback writes; finalization interruption; dropped/truncated writes; multibyte byte limits; invalid/future schemas; digest-consistent invalid roster; payload loss/extra chunks; stale revision/lineage; head/journal changes during reads; namespace preservation; true large→small→large transitions deleting obsolete slots; and 100 further bounded commits. New regressions reproduce all three preservation gaps, prove refusal before overwrite/delete, authenticate an exact historical token rather than counters alone, and hold late foreign metadata/unrecognized bytes. Independent in-memory negative controls remove prior-standby authorization or cleanup ownership checks and reproduce the unsafe overwrite/deletion, without changing the real module. The existing 60 accounting checks are unchanged.

A future real integration needs a portable bounded SHA256 implementation, cooperative work slices for hashing/serialization/readback under existing scheduling, strict one-owner commit sequencing, native property/save/rejoin tests and a confirmed persistence model. There is no native save/flush call or LevelDB transaction in this experiment. A power failure could expose a published head before its data is durable; the reader will refuse missing/corrupt data, but no lossless recovery guarantee is claimed. It cannot reconstruct an unpersisted death event or authenticate caller-supplied archive/engagement barriers. It validates saved-state invariants and revision linkage, not the legitimacy of arbitrary gameplay mutations supplied by a caller; production must publish only the sole authoritative reducer's accepted transaction.
